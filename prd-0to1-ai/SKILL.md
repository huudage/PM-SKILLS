# 从 0 到 1 构建 AI 产品 PRD（prd-0to1-ai）

## Purpose

把用户零散抛出的「背景 + 目标人群 + 想要的功能」逐步打磨成一份工程可执行、决策可追溯的 **AI / RAG 产品 PRD**。

本 skill 的工作方式不是一次性套模板生成，而是**分模块增量构建 + 对话驱动补全**：
- 全程维护两个**项目本地 md 看板**——一个沉淀已知（记忆），一个跟踪进度（现状）。
- 对缺失且影响质量的信息，**主动追问用户**，绝不用通用套话或臆测填空。
- 需要方向性取舍时，**触发决策门**交用户拍板，而非替用户决定。
- 可随时中断、下次凭两个看板恢复。

**适用：** 产品从 0 到 1、面向 AI/RAG 类产品的首版 PRD。
**不适用：** 基于现有产品的功能优化型 PRD（属另一个 skill，暂未构建）；小改动/单功能 spec（杀鸡用牛刀）。

---

## Key Concepts

### 两个看板（项目本地 md，仅本项目，不写入全局 memory）

**看板 A — 长期记忆看板**（模板 `templates/board-A-memory.md`）
在本项目整个构建周期内长期有效。四部分：
1. 已确认事实（Facts）—— 产品定位、用户、约束、已拍板的决策
2. 项目偏好（Preferences）—— 写法/范围松紧/技术选型/决策风格
3. 指代关系 / 术语表（References）—— 别名、缩写、实体映射
4. 待澄清（Open）—— 尚未确认、不能当事实用的疑问

**看板 B — 构建现状看板**（模板 `templates/board-B-status.md`）
反映当下状态，可中断恢复。含进度总览表 + 每模块详情（状态 / 构建 plan / 缺失信息 / ⛔待决策 / PRD 锚点）。状态取值：未开始 / 进行中 / 已落地。

> 两者分工：A 是「沉淀下来的知识」，B 是「动态的进度与待办」。构建任一模块前先读 A，产出后更新 B，新确认的事实/偏好/指代回写 A。

### 模块清单

**固定模块（5 个，必做）**
1. 产品目标与范围（Why/How/What + 目标用户与使用场景）
2. 核心工作流与目的（PRD 核心）
3. AI 核心人设（系统提示词 / 对话逻辑 / CoT）
4. 前端设计 + 后端架构（含字段清单）
5. 异常处理与兜底策略

**可选模块（默认不做，按项目特征经对话确认后才纳入）**
- 成功指标与度量（含 AI 质量指标）
- 数据与知识来源 + 检索策略（RAG 产品强烈建议）
- 模型选型与配置
- AI 质量评估与测试（Evals）
- 安全、合规与护栏
- 上线、迭代与反馈闭环
- 范围外（Out of Scope）
- 依赖、风险与开放问题

### 对话驱动 / 缺口优先（核心原则）
- 构建模块前先读看板 A 与用户已给材料，**只就缺失且影响该模块质量的信息发问**——已知的不重复问。
- 缺信息就**积极追问**，不臆测、不用通用套话填空。
- 一次一问或小批量，最重要的先问，避免一次抛十个问题。

### 决策门
两类卡点要分清：
- **信息缺失** → 主动追问用户补全（普通追问）。
- **方向性取舍 / 多个合理方案并存** → 触发 **⛔决策门**：在看板 B 标记，明确列出选项 + 各自适用场景 + 你的推荐，请用户拍板。不替用户做方向性决定。

## Application — 运行流程

### Phase 0 · 接收初始信息
接受用户任意形式的输入：背景信息、目标人群、想要的功能、上传的文档等。先完整读取、不急着问。

### Phase 1 · 确定大纲模块（建看板）
1. 固定的 5 个模块**始终纳入**。
2. 评估产品特征，**逐项提议**是否纳入可选模块并说明理由（例：判断是 RAG 产品 → 提议纳入「数据与知识来源 + 检索策略」；面向对外发布/合规敏感 → 提议「安全合规与护栏」）。由用户拍板。
3. 在 PRD 项目目录下，从 `templates/` 复制初始化三个文件：
   - `board-A-memory.md`、`board-B-status.md`、`PRD-{{产品名}}.md`（基于 `prd-skeleton.md`）
4. 把确认的模块清单写入看板 B 进度总览（固定 + 已纳入的可选）。

### Phase 2 · 用已有信息初填
1. 从 Phase 0 的输入里抽取已知事实、偏好、指代 → 写入**看板 A**。
2. 把能填的内容**简单填入** PRD 对应模块（不强行编造）。
3. 在**看板 B** 标注每个模块的初始状态与已识别的缺口。

### Phase 3 · 缺口追问循环（逐模块推进）
按模块循环，每个模块：
1. 读看板 A + 当前 PRD 内容，列出该模块的**缺失信息**与**潜在决策点**，写入看板 B。
2. **追问**缺失信息（遵守对话规则）；遇方向性取舍触发**决策门**。
3. 用户答复后：更新 PRD 该模块内容 → 看板 B 状态推进（进行中/已落地）→ 新事实/偏好/指代回写看板 A → 关闭已解决的缺口与决策门。
4. 模块「已落地」标准：核心问题已答、无悬而未决的决策门、内容足以指导下游（设计/研发）。

> 可随时中断。恢复时先读两个看板还原上下文，再从看板 B 中未完成的模块继续。

### Phase 4 · 综合输出成品 PRD
当看板 B 各模块「差不多齐」（固定模块全部已落地、无未决决策门、关键可选模块完成）时：
1. **综合**看板信息与各模块已落地内容，生成连贯的成品 PRD（统一口径、消解指代、补全过渡）。
2. 删除 PRD 骨架里未纳入的可选模块占位。
3. 在文末附「未决项」（若仍有 Open/低优先缺口），并提示可借鉴 red-team 思路对承重假设做一次自检。

## 文件与目录约定
在**当前 PRD 项目目录**下维护（不是 skill 目录）：
```
PRD-{{产品名}}.md        # 成品/在建 PRD
board-A-memory.md        # 看板 A
board-B-status.md        # 看板 B
```
若用户未指定目录，先询问或就近在工作目录创建，并把路径记入看板 A 偏好。

## 模块构建指引

> 每个模块给出：**目的** · **关键追问**（缺口优先，按需问）· **AI 特化要点** · **落地标准**。

### 固定 1 · 产品目标与范围（Why/How/What + 用户与场景）
- 目的：讲清为什么做、为谁做、做什么、边界在哪。
- 关键追问：解决什么痛点？为什么是现在？目标用户是谁、典型场景、现状/替代方案？本期范围边界？
- AI 特化：明确 AI 在产品价值中的位置（是核心能力还是辅助）。
- 落地标准：Why/用户场景/What 三者可被下游读懂，范围有明确边界。

### 固定 2 · 核心工作流与目的
- 目的：刻画最核心的端到端主流程及每步目的。
- 关键追问：用户从进入到拿到价值的步骤？每步谁来做（AI/规则/人工）？关键分支？
- AI 特化：标明哪些步骤由 AI 完成、与检索/工具/人工如何衔接。
- 落地标准：主流程步骤完整、每步目的清晰、AI 与非 AI 边界明确。

### 固定 3 · AI 核心人设（系统提示词 / 对话逻辑 / CoT）
- 目的：定义 AI 是谁、怎么说话、怎么思考、边界在哪。
- 关键追问：人设定位与语气？能做/不做什么？多轮对话如何澄清与收束？哪里需要 CoT、是否对用户可见？
- AI 特化：产出**系统提示词草案**；说明 CoT 与工具调用/检索的配合方式。
- 落地标准：有可用的 system prompt 草案 + 对话逻辑 + CoT 策略。

### 固定 4 · 前端设计 + 后端架构（字段清单）
- 目的：给出前端风格/关键界面，以及后端架构与数据模型。
- 关键追问：前端风格基调与关键页面？后端模块/服务划分？核心实体有哪些、各自字段？关键接口？
- AI 特化：RAG 产品需体现检索链路；区分需用户提供的事实与**由你完善的技术细节**（字段类型、约束等可由你补全初稿再让用户校验）。
- 字段清单格式：见骨架 §4.3，按实体重复 `字段名/类型/必填/说明/示例/约束`。
- 落地标准：前端有可执行的风格与界面描述；后端有模块划分 + 核心实体字段清单。

### 固定 5 · 异常处理与兜底策略
- 目的：覆盖失败与边界场景的系统行为。
- 关键追问：哪些失败场景（模型超时/检索为空/低置信/越权/超长输入）？各自系统怎么做、给用户什么反馈、是否升级人工？
- AI 特化：重点覆盖 AI 特有失败——幻觉、检索命中为空、低置信、被诱导越权。
- 落地标准：关键异常场景成表覆盖，每条有系统行为 + 用户反馈 + 兜底/升级。

### 可选模块（纳入后简述要点）
- 成功指标与度量：主/次/护栏指标 + AI 质量指标（准确率、有用性、拒答率等），指标须可量化（含基线→目标→测量方式）。
- 数据与知识来源 + 检索策略：知识来源、切分/索引、召回策略、新鲜度与更新机制（RAG 命脉）。
- 模型选型与配置：模型、上下文窗口、参数、降级备选模型。
- AI 质量评估与测试（Evals）：评测集、评测方法（自动/人工/LLM-as-judge）、回归基线。
- 安全、合规与护栏：内容审核、Prompt 注入防护、PII/隐私、越狱防护。
- 上线、迭代与反馈闭环：灰度/AB、反馈如何回流改 prompt 与知识库。
- 范围外（Out of Scope）：明确不做什么及原因。
- 依赖、风险与开放问题：外部依赖、风险与缓解、待决策清单。

## 对话与提问规则
- 缺口优先：只问看板 A 没有、且影响当前模块质量的信息。
- 节奏：一次一问或小批量，先问最关键的。
- 不臆测：信息不足时追问，不要用通用模板话术填充。
- 决策门：方向性取舍要列「选项 + 各自适用 + 推荐」，交用户拍板。
- 每次产出后即时回写看板 A、推进看板 B，保持两者与 PRD 一致。

## Examples

**典型一轮：**
```
用户：做一个面向法律从业者的合同审查助手，能上传合同、自动标出风险条款。
Agent：
  · Phase1 判断为 RAG 产品 → 固定 5 模块纳入，提议纳入「数据与知识来源+检索策略」
    「安全合规与护栏」（合同含敏感数据），询问用户是否纳入。
  · 初始化三文件，把「目标用户=法律从业者」「核心功能=合同上传+风险条款标注」
    写入看板 A，初填 PRD §1。
  · 进入模块1追问缺口：风险条款的判定依据来自哪？（法规库/企业模板/用户自定义？）
    —— 这是决策门，列选项请用户选。
```

**中断恢复：** 读 `board-A-memory.md` + `board-B-status.md` → 找到看板 B 中状态为「进行中」的模块 → 从其缺口继续。

## Common Pitfalls

1. **臆测填空**：信息缺失时编内容而非追问。后果：PRD 看似完整实则空心。纠正：缺口优先，主动问。
2. **替用户做方向决策**：把本该用户拍板的取舍自行定了。纠正：触发决策门、列选项。
3. **看板与 PRD 失同步**：产出后忘了回写。纠正：每次产出后立即更新两个看板。
4. **可选模块默认全开**：不评估就堆模块。纠正：逐项按项目特征提议、用户确认。
5. **过早输出成品**：模块未落地、决策门未关就生成终稿。纠正：满足 Phase 4 条件再综合输出。
6. **重复发问**：问已在看板 A 的内容。纠正：提问前先读看板 A。
